## 1. Why this milestone exists

twinBook's whole design rests on a few things the browser engine must be able to do.
M1 proves them, or disproves them, before any Facebook traffic or account is involved.
It is a gate: its result decides whether the architecture in `docs/PLAN.md` stands.

The background you need: Facebook's web client contains an anti-tampering system
that detects JavaScript hooks on `XMLHttpRequest`, `fetch` and `JSON.parse` inside the
page and routes around them. So twinBook never modifies anything in the page's
JavaScript realm. It filters responses one layer below, in the network stream, from a
WebExtension background script using Gecko's `webRequest.filterResponseData`. The page
must receive already-filtered bytes and see only untouched native functions.

Everything in M1 runs against a local mock server that imitates the shape of
Facebook's traffic. No request may go to any Facebook or Meta host.

M1 also leaves behind real, reusable code: the `:engine` module, the bridge between
Kotlin and the extension, the streaming filter core, and the mock server. Later
milestones build directly on them, so write them as product code, not as a demo.

## 4. Decisions already made

Do not reopen these. If one proves impossible, that is a gate finding to report.

1. GeckoView is used directly inside `:engine`. One `GeckoRuntime` per process.
2. twin-bridge is the only extension in M1. It is installed as a built-in extension
   from the APK assets under `assets/extensions/twin-bridge/`.
3. Response filtering runs only in the extension background script through
   `webRequest.filterResponseData`. No content script and no injected script may touch
   a page that runs a site's own JavaScript application.
4. The bridge is one long-lived native messaging port opened by the background script,
   carrying JSON messages, with request and response correlation in both directions.
5. The mock server runs inside the instrumented test process on the device, bound to
   loopback. Tests are hermetic: no host-side process is needed.
6. ABIs: `x86_64` and `arm64-v8a` only.
7. Fail open. If the filter cannot parse something, the original bytes pass through
   unchanged and an error is reported to the app. The filter must never break a page.

### 5.2 twin-bridge extension

Add only the permissions you use. Expected: `webRequest`, `webRequestBlocking`,
`nativeMessaging`, `geckoViewAddons`, and host permissions.

- **Bridge client.** Connect the native port on startup, route messages, correlate
  requests and responses, queue until connected.
- **Streaming filter core**, as pure library code under `src/lib/` with Vitest tests.
  Input is a sequence of byte chunks, output is a sequence of byte chunks. It handles:
  - newline-delimited JSON, one document per line;
  - an optional `for (;;);` guard before the first document, preserved in the output;
  - chunk boundaries anywhere, including inside a line and inside a multi-byte UTF-8
    character;
  - prompt output: a complete line is emitted as soon as it is complete. The filter
    must not hold the whole response;
  - a pluggable rule deciding what to drop. For M1 the rule is a mock marker, see 5.3.
    The real rule engine arrives in M4;
  - untouched lines forwarded byte for byte, not re-serialized;
  - fail open on any parse error.
- **webRequest wiring.** Apply the filter to matching XHR and fetch responses, and a
  simple document filter to matching main-document HTML responses.
- **Request recorder.** For POST requests to the mock GraphQL path, read the request
  body and send the app an event with the form fields a Facebook request carries:
  `fb_api_req_friendly_name`, `doc_id`, `variables`, `fb_dtsg`, `lsd`, `jazoest`,
  `__rev`, `__req`, and the full field-name list.
- **Replay executor.** On request from the app, perform an HTTP request and return
  status, headers and body through the bridge. Two interchangeable paths, see 5.5.
- **Lint policy.** `web-ext lint` errors fail the check. Warnings fail unless they are
  listed in a committed allowlist file with a reason per entry. GeckoView-only
  permissions are the expected entries.

### 5.3 Mock server and test page

Build a mock that imitates the shape of Facebook's traffic. The shapes below are the
planner's best current knowledge and are good enough for M1. Real shapes are captured
in M2.

- A GraphQL-like endpoint accepting a form-encoded POST and answering with a streamed
  body: several JSON documents separated by newlines, flushed in separate chunks with
  controllable delays. The first document carries a list at
  `data.viewer.news_feed.edges`. Later documents each deliver one more edge, with a
  `path` such as `["viewer","news_feed","edges",3]` and an `extensions.is_final` flag
  that is `true` only on the last document.
- Mock ad marker: an edge whose `node` contains `"mock_sponsored": true` is an ad.
  Expected filter behaviour: remove such edges from the list in the first document,
  drop a later document entirely when its edge is an ad, and if the dropped document
  is the final one, emit a minimal replacement that still carries `is_final: true`.
- Scenarios selectable per request: chunk boundary inside a line; boundary inside a
  multi-byte character; with and without the guard prefix; gzip content encoding; a
  5 MB response; a malformed line in the middle; ads at first, middle and last position.
- An HTML document endpoint with a JSON island inside a `<script type="application/json">`
  element that contains ad edges, for the document filter.
- Session endpoints: one that sets cookies of each kind (plain, `HttpOnly`,
  `SameSite=Lax`, `SameSite=None; Secure` if loopback allows it), and one that echoes
  back the cookies and request headers it received as JSON.
- A tiny static page with no scripts, to act as an "anchor page" (see 5.5).
- A report endpoint where the test page posts its results, so tests read results from
  the server and not from the page's DOM.
- The test page itself. Its script requests the GraphQL endpoint through
  `XMLHttpRequest` with progress events and through `fetch` with a stream reader,
  records arrival time and content of each line, and runs the integrity checks of 5.4.

### 5.4 Integrity checks inside the page

The page's own script verifies that nothing in its realm was touched while filtering
is active. At minimum: `XMLHttpRequest`, its prototype methods `open` and `send`, the
`responseText` getter, `fetch`, `JSON.parse`, `Response.prototype.json` and
`Function.prototype.toString` all stringify as native code; the check
`Function.prototype.toString.toString === Function.prototype.toString` style identity
holds; calling these through a freshly created same-origin iframe gives the same
results; no unexpected global and no injected element exists. The page posts the
outcome to the report endpoint.

### 5.5 Sessions, persistence and replay probes

- **Two sessions.** One with a mobile user agent, one with a desktop user agent, in
  the same runtime. The server must see the two different user agents, and a cookie
  set through one session must be sent by the other.
- **Headless session.** A session attached to no view loads the test page, runs its
  requests, gets filtered responses, and its timers keep running.
- **Persistence.** Cookies and the extension's `storage.local` survive a full process
  kill and relaunch. Instrumented test runs normally clear app data, so this needs
  its own script that drives `adb` directly. Add it under `tools/`.
- **Extension update.** Evidence that a changed extension in a reinstalled APK takes
  effect with app data kept.
- **Replay probes.** M5 will fetch data on the app's behalf without a full page
  loaded. Probe the two candidate paths against the mock and record, for each, exactly
  what the server received:
  - Path A: `fetch` from the extension background script with credentials included.
    Also try rewriting `Origin` and `Referer` to the site origin in a blocking
    `onBeforeSendHeaders` listener, and record which rewrites Gecko honours.
  - Path B: `fetch` executed in the context of the anchor page, a same-origin page
    with no site JavaScript, in a headless session. This is the one place a content
    script is allowed, because no site application runs on that page.
  - For each path record: which cookie kinds were sent, including `HttpOnly` and a
    cookie set by the other session; `Origin`; `Referer`; `Sec-Fetch-Site`,
    `Sec-Fetch-Mode`, `Sec-Fetch-Dest`; `User-Agent`; and whether the body came back
    to Kotlin intact. Run the probes under the engine's default tracking-protection
    settings and under its strict settings, and state what those defaults are.
