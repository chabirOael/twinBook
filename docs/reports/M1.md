# M1 report: engine gate

Branch `m1-engine-gate`, build agent run on 2026-10-02. Device: emulator `twinbook_api36`
(Android 16, x86_64, KVM). GeckoView 157.0.20260924084938.

## 1. Gate verdict

**Pass with reservations.** All 14 core checks (G1 to G14) and both persistence checks (G15,
G16) pass, in a fresh clone of the branch for G1 and for the full instrumented suite. The
reservations: GeckoView needed two start-up workarounds that the design now depends on
(section 7, findings 1 and 2), and the replay probes ran on a single loopback origin, so they
say nothing yet about cross-site behaviour against the real site.

## 3. Replay probe results

`ReplayProbeTest`, run with `tools/engine-instrument.sh ReplayProbeTest` (the same test also
passes in the Gradle suite). For each tracking-protection level, the test opens three new
sessions: a mobile one and a desktop one, which each set one cookie of every kind
(`a<level>_*` and `b<level>_*`), and a headless desktop session showing the anchor page.
Each probe POSTs a form body to `/session/echo` with `credentials: "include"`. The table shows
what the mock server received. The site origin is `http://127.0.0.1:<port>`; the background
script's origin is `moz-extension://<uuid>`.

"Cookies" lists the kinds sent from each setter: plain, HttpOnly, SameSite=Lax,
SameSite=Strict, SameSite=None;Secure. "Body" means the echoed body, with an 11 KB multi-byte
payload, came back to Kotlin over the bridge and matched exactly.

**Default** (GeckoView defaults: ETP level 0 = none, anti-tracking categories 46 = DEFAULT,
cookie behaviour 5 = ACCEPT_FIRST_PARTY_AND_ISOLATE_OTHERS, strict social tracking protection
off, cookie purging off, session `useTrackingProtection` false):

| Path | Cookies (set by A / by B) | Origin | Referer | Sec-Fetch-Site | Sec-Fetch-Mode | Sec-Fetch-Dest | User-Agent | Body |
|---|---|---|---|---|---|---|---|---|
| A: background fetch | all 5 / all 5 | `moz-extension://<uuid>` | absent | same-origin | cors | empty | mobile (runtime default) | intact |
| A + Origin/Referer rewrite | all 5 / all 5 | site origin | `<site>/` | same-origin | cors | empty | mobile | intact |
| A + Origin/Referer/UA rewrite | all 5 / all 5 | site origin | `<site>/` | same-origin | cors | empty | desktop (rewritten) | intact |
| B: anchor `content.fetch` | all 5 / all 5 | site origin | `<site>/anchor` | same-origin | cors | empty | desktop (the anchor session's) | intact |
| B': anchor content-script `fetch` (extension principal) | all 5 / all 5 | absent | absent | same-origin | cors | empty | mobile | intact |

**Strict** (ETP level 2, anti-tracking 766 = STRICT, strict social tracking protection on,
cookie behaviour 5, new sessions with `useTrackingProtection` true): **identical to the default
table, row for row.**

Exact UA strings: mobile `Mozilla/5.0 (Android 16; Mobile; rv:157.0) Gecko/157.0 Firefox/157.0`,
desktop `Mozilla/5.0 (X11; Linux x86_64; rv:157.0) Gecko/20100101 Firefox/157.0`.

The headers the extension saw in `onSendHeaders` matched what the server received in every
row. Gecko honours rewriting `Origin`, `Referer` and `User-Agent` in a blocking
`onBeforeSendHeaders` listener for the extension's own requests. Neither path adds
`Sec-Fetch-User` or an `X-Requested-With`-style header.

**G19 verdict.** Yes: both paths send every cookie kind, including HttpOnly, SameSite=Strict
and cookies set by another session. Both return the body to Kotlin intact. Path B sends
`Origin` equal to the site origin with no help; path A does so once `Origin` is rewritten,
which Gecko honours. **Recommendation for M5: path B (anchor page) as the primary replay path,
with path A as the fallback.** Reasons:
- Path B's requests are the browser's own page requests: the site's origin, a same-origin
  Referer, and the UA of the (desktop) session that holds the anchor, with no header surgery.
- Path A needs three rewrites (Origin, Referer, UA) to look the same, and any header Gecko adds
  in future that we do not rewrite would mark it.
- Path B costs one headless session on a scriptless same-origin page. Its memory cost was not
  measurable here, because it shares a content process with other same-origin sessions.

Caveat that M2 or M5 must close: everything here was one loopback origin, so "same-origin"
cookies and `Sec-Fetch-Site` say nothing about how Gecko treats a `moz-extension://` request
to the real site over HTTPS. Tracking protection also had nothing to act on, because no
request was third-party. The anchor page for the real site also still has to be chosen: a
same-origin URL that serves a document with no scripts.

## 7. GeckoView findings

1. **Installed extensions start their background script late.** GeckoView starts them on
   `extensions-late-startup`, which `geckoview.js` sends when the first session window opens
   (via `DelayedInit`, at most 15 s). A fresh install starts the background at once, so this
   only shows on the second start. With no session, the bridge never connected. `Engine` now
   opens a bootstrap session at start and closes it when the bridge connects. Until the
   background runs, no webRequest listener exists: site pages must load only after
   `awaitReady()`.
2. **Gecko can lose an add-on's startup state.** Gecko writes `addonStartup.json.lz4` a moment
   after an install. A test process killed about 1 s after installing left a profile with the
   add-on in `extensions.json` but no `addonStartup.json.lz4`. From then on, every start logged
   `Force scan SCOPE_ALL locations on empty XPIStates locations data`, `ensureBuiltIn` returned
   the add-on (same version, so no reinstall), and the background never started. `Engine` now
   reinstalls with `installBuiltIn` if the bridge has not connected 10 s after install. Seen
   working: `twin-bridge background did not start within 10000 ms; reinstalling`, then
   `background started` 108 to 207 ms later (two occurrences); storage.local survived. This also matters for app
   updates: if the app is killed right after updating, the next start costs 10 s.
3. **Version check is `!=`** (`GeckoViewWebExtension.ensureBuiltIn`), so lower versions
   reinstall too. The per-build stamp makes every changed build take effect.
4. **Messaging:** `WebExtensionController` queues `connectNative` until `setMessageDelegate`
   (`releasePendingMessages`). Port messages go through a per-port `EventDispatcher`. JSON key
   order is lost across the port (GeckoBundle). The extension re-sends hello until welcomed.
   A 1 MB message round trip took 119 to 206 ms.
5. **Stream filter:** receives decoded bodies (gzip transparent). It works from
   `onBeforeRequest` for XHR/fetch and from `onHeadersReceived` for documents. Its chunk sizes
   vary run to run (49 to 96 chunks for the same 5.9 MB). No limit was hit at 5.9 MB.
6. **Headless sessions** load, run scripts and keep full-speed timers when kept active
   (29 ticks of a 100 ms interval in 3 s). They need no view.
7. **Cookies:** one jar for all sessions of the runtime. Loopback HTTP accepts
   `SameSite=None; Secure`. Extension `fetch` with host permissions sends SameSite=Strict
   cookies and reports `Sec-Fetch-Site: same-origin`.
8. **Process model:** with no session, five processes run (main, crash helper, GPU, two
   content processes). Same-origin sessions share a content process. Closing a session does
   not shrink PSS right away.
9. **Defaults:** ETP level 0 (none) unless set. `useTrackingProtection` is false per session by
   default.
10. **Thread rules:** `GeckoSession.getUserAgent()` and `GeckoView.capturePixels()` assert the
    main thread. GeckoResult callbacks go to the registering thread's Looper.
11. **Initial about:blank:** every new session reports a start and stop for about:blank, which
    can arrive after a load issued right after `open()`. This raced `loadAndWait` until fixed.
12. **Emulator rendering:** SwiftShader renders the lab page correctly (pixel check passes).
    The first `capturePixels` can lag a few frames, so the test retries.
13. **Noise:** closing a session right after its first load logs
    `TypeError: can't access property "WindowEventDispatcher", win is null` from
    `GeckoViewSessionStore.sys.mjs`. Harmless.

## 8. Deviations

1. **Bootstrap session and reinstall recovery in `Engine`** (findings 1 and 2). Not in the
   prompt. Without them the engine does not reliably reach "ready".
2. **`storage` permission** added: G15 needs `storage.local`. Everything else is from the
   expected list.
3. **Mock server is its own pure-JVM Gradle module** (`:mockserver`), handwritten, no library.
   That lets its scenarios run in `tools/check.sh` as JVM tests and keeps it reusable by :app
   tests later.
4. **Extension packaging moved into `:engine`'s generated assets** instead of the app. The
   app gets it through the library merge; `unzip -l` shows one copy.
5. **Stream-filter device tests run in headless sessions.** Visible sessions are covered by the
   lab test (G2) and the memory probe. The headless test (G14) runs the same scenario plus
   integrity checks.
6. **Memory measured in the :engine test app**, not the product app, because only there can the
   four stages be driven deterministically. Start-up was measured in the app.
7. **No `@MainThread` annotations**: `androidx.annotation` is only a runtime dependency of
   GeckoView, and the prompt's dependency list does not include it. KDoc says "Main thread
   only" instead.
8. **Extra probe rows:** a UA rewrite on path A, and the content script's own `fetch` (B') for
   comparison. Extra scenarios: `no-ads`, `slow`.
9. **Document filter applies to every `text/html` main or sub frame on the target hosts**, not
   to a path. The test page itself goes through it; G12 shows that.
10. **Native libraries packed compressed** (`useLegacyPackaging = true`) in the app and the
    engine test APK. This gives a 198 MB APK instead of roughly 400 MB with uncompressed,
    page-aligned libraries, at the cost of extraction at install.
11. **`PersistenceProbe` and `MeasurementProbe` are excluded from Gradle connected runs**
    (`@ManualProbe` plus the `notAnnotation` runner argument); only the scripts run them.
12. **`tools/emulator-start.sh` changed** to work around the `XDG_RUNTIME_DIR` deadlock.
13. The first commit has exactly the prompt's message and no trailer. Later commits end with a
    `Co-Authored-By` trailer.

## 9. Problems and risks

- **Emulator deadlock in IDE or agent shells.** The emulator hung at boot several times
  (`detected a hanging thread`, then qemu crashed on purpose). Cause, reproduced on purpose:
  `XDG_RUNTIME_DIR=/run/user/1000/` points to a directory that does not exist, and netsimd
  fails with `Permission denied`. `env -i` hid it. Fixed in the script; documented.
- **Start-up correctness rests on two workarounds** (findings 1, 2). A future GeckoView may
  change `extensions-late-startup` timing. Recovery costs 10 s when it triggers.
- **Pages loaded before `awaitReady()` are not filtered.** M3 must gate the first site load on
  readiness.
- **Process kill right after install or update** is a real-world case (OOM, user swipe). The
  recovery handles it, and G16 only covered the clean case.
- **Probes are single-origin** (section 3 caveat). Real cross-site and HTTPS behaviour is
  unverified.
- **Filter parses every line** with `JSON.parse`. Mock lines are 1 KB; real GraphQL lines can
  be hundreds of KB. The 5.9 MB measurement (26 to 68 ms) is encouraging but not proof.
- **Event volume:** one `filter.stats` per filtered response plus `recorder.request` per POST.
  The bridge's replay buffer is 64 events. Fine for M1; with real traffic consider sampling.
- **Memory:** 451 MiB PSS before any page, 558 MiB with one. The host peaks at 10.2 GB plus
  2.5 GB swap while Gradle and the emulator run together.
- **APK size** 198 MB debug; installs take about 10 s on the emulator.
- **KVM access** is still the temporary `chmod 666` (`crw-rw-rw- root kvm`). It will be lost
  on the next WSL restart unless the owner applies the group fix.
- **`diag.*` handlers ship in the production extension.** They only echo and count, but they
  let any app-side code make the extension call back into the app.
- **Version stamp collision:** two different builds share a stamp with probability 1 in 2^28.
  A collision would silently keep the old extension.

## 10. Questions for the planner

1. Do you accept the bootstrap session and the 10 s reinstall recovery as the engine's
   start-up contract? The alternative is calling `installBuiltIn` on every start, which costs
   a reinstall (108 to 207 ms in the recovery case) on every start.
2. M5 replay path: do you adopt path B (anchor page) as primary with path A as fallback, as
   recommended in section 3? If so, M2 should identify a scriptless same-origin anchor URL on
   the real site.
3. Should the `diag.*` bridge methods be compiled out of non-debug builds (a build flag in
   `build.mjs`), or stay as harmless diagnostics?
4. Debug native-library packaging: keep compressed (smaller APK, faster installs) or switch
   to uncompressed now to measure the release configuration early?

## 11. Suggestions for M2 and later

- **Service worker.** The site's web client registers a service worker. Responses it serves
  from its cache, or fetches itself, may never reach the stream filter, or reach it with no
  tab. M2 should record whether GraphQL and document responses pass through the service
  worker, and whether `filterResponseData` sees them.
- **Real stream shapes.** Check the guard prefix, the line separators, very long lines, and the
  real incremental payload fields (`label`, `path`, `is_final`, possibly `@defer`/`@stream`
  variants). Also check the real Content-Type of GraphQL responses (the filter keys on path and
  request type, not content type).
- **Real HTML islands.** They are large. The island filter buffers one island at a time, so
  measure the biggest island and the time to first paint with the document filter on and off.
- **Encodings.** Confirm Brotli and zstd responses arrive decoded, as gzip does
  (`Accept-Encoding: gzip, deflate, br, zstd` is sent).
- **Observe-only mode.** Add a rule mode that counts and reports matches but keeps every
  line, so M2 can run the filter against real traffic without changing it. The
  `filter.setEnabled` switch exists; a dry-run decision type would be the next step.
- **Recorder.** Record request headers too (for example any friendly-name or LSD header).
  Record GET GraphQL requests and the query string, not only POST bodies.
- **Cross-site replay.** Repeat the section 3 probe against the real site with the test
  account. In particular check path A's `Sec-Fetch-Site` and SameSite handling for a
  `moz-extension://` request to an HTTPS site.
- **Login cookies.** G15 showed session cookies are dropped at restart. Check which of the
  site's login cookies carry an expiry; if a needed one is session-only, M3's "login survives
  restart" will fail.
- **Gate the first load on readiness** (finding 1) in M3's shell.
- **Tracking protection.** GeckoView defaults to ETP level 0. Decide in M3 whether to enable
  standard ETP. It should not touch the first-party site, but the probe could not show that.
- **PLAN.md updates proposed:** in section 3, record GeckoView facts 1 to 3 of section 7. In
  section 8, add "load site pages only after `Engine.awaitReady()`" and "built-in extension
  versions are stamped per build". In section 7, keep the KVM group fix open.
